# 后台管理系统

后台已按 Phase 0–20 全部落地并在线上实际使用。后续改动沿用「一次一个阶段、每阶段停下确认」的协议。

**能力**：增删改查、批量操作、标签与作者合并管理、玩法 / 机制 / 平台词表、作品关系、
图片上传（自动缩放 + WebP）、未保存草稿预览、行内上下线与永久删除、GameJolt 半自动导入、
操作署名、只读资料质量检查。

## 1. 路由

全部挂在 `AdminLayout` 下，Hash 形态：

| --- | --- | --- |
| `/#/admin` | → `admin-games` | 重定向 |
| `/#/admin/login` | `AdminLogin.vue` | **唯一豁免认证的后台路由** |
| `/#/admin/games` | `AdminGames.vue` | 列表：搜索 / 筛选 / 排序 / 分页 / 批量 / 行内操作 |
| `/#/admin/games/new` | `AdminGameEditor.vue` | 新建 |
| `/#/admin/games/:id/edit` | `AdminGameEditor.vue` | 编辑 + 永久删除 |
| `/#/admin/preview` | `AdminGamePreview.vue` | 未保存草稿预览 |
| `/#/admin/taxonomy` | `AdminTaxonomy.vue` | 标签与作者合并管理 |

移动端菜单与页脚）。入口对访客可见，但进入即被登录门禁拦下 —— **真正保护数据的是令牌权限**。

## 2. 认证

**没有自建账号体系。** 凭据是一枚 **GitHub 细粒度 Personal Access Token**：
站长签发，只授权**数据仓**、只给 `Contents: Read and write`。

于是「管理员只能改数据、不能碰代码」由**凭据权限本身**保证，而不是我们写的判断逻辑
（2026-09-30 实测：拿这枚令牌往代码仓写文件被 GitHub 拒绝）。

| 环节 | 做法 |
| --- | --- |
| 门禁 | `src/router/authGuard.ts` 的 `beforeEach`，判据 `to.meta.requiresAuth` |
| 安全默认值 | `requiresAuth: true` 写在 `/admin` **父记录**上，子路由覆盖。新增后台页面默认受保护 |
| 登录 | `/#/admin/login`：粘贴令牌 → 校验 → 存本机 `localStorage` |
| 登出 | 后台 Header「登出」：清除令牌并回登录页 |
| 令牌位置 | **只在本机浏览器**，不进代码、不进仓库 |

**校验分两步，缺一不可**：① `/user` 确认令牌有效；② 读一次数据仓 `db.json` 确认真的够用。
只做 ① 的话「登录成功」是骗人的 —— 令牌有效但没授权数据仓时，用户会一路进到后台、
在第一次保存时才炸。

错误信息收口在 `src/services/githubApi.ts`，全部翻译成能照着做的中文：
401 →「令牌无效或已过期，请重新生成」；403 →「确认已授权数据仓，且 Contents 权限为 Read and write」；
404 →「确认令牌已授权数据仓，且仓库里有 db.json」。

> ⚠️ 认证状态是**模块级 ref**，只在模块加载时读一次 localStorage。外部改了本机存储后
> 必须重新加载页面（或调用 `reloadStoredToken()`）。已挂 `storage` 事件监听做跨标签页同步。
>
> ⚠️ 守卫单独放在 `src/router/authGuard.ts`：`router/index.ts` 会创建带 hash history 的真实 router
> （Node 里没有 `location`），从那里导出会把冒烟测试搞崩。冒烟测试为此装了 localStorage 桩并调用
> `installAuthGuard()`，**门禁本身也在冒烟覆盖之内**（含「未登录被拦」用例）。

## 3. 写入落在哪里

**登录后：写进数据仓。** `GitHubGameRepository` 通过 GitHub Contents API 读写
`fnaf-fan-games-data/db.json`。

| 环节 | 做法 |
| --- | --- |
| 读 | `GET /repos/…/contents/db.json` → base64 解码 → `normalizeGames()` |
| 写 | **读最新内容 + 最新 sha → 把改动重放到最新内容上 → 带 sha 提交** |
| 并发 | sha 不匹配时 GitHub 返回 **409** → 自动重读重放重提交（最多 3 次） |
| 提交信息 | `（后台）更新《作品名》的 status、tags` —— 用**最新**内容生成，让历史读得懂 |
| 编码 | `btoa` 只吃 latin1，中文会炸 → 必须先编 UTF-8 字节（`encodeBase64`） |

> ⚠️ `db.json` 是**单个文件**，任意两人同时保存都会冲突（不只是改同一条时）。
> 敢直接重试是因为**重放永远正确**：改的是「某一条作品的某几个字段」，不是一段文本 ——
> 与合并文本 diff 有本质区别。有专门断言守着（包括「重放没有覆盖别人刚改的东西」）。
>
> 写路径只落盘**显式改动的字段**：未编辑作品整条原样写回；编辑器附带的未变化 `relations`
> 不算修改；词表改名 / 合并只 patch 分类字段；删除作品只清理指向它的入边。
> 归一化结果只服务读取与展示，`check:data` 仍能看见数据仓里的历史关系问题。

**未登录 / 本地模式：写进本机 localStorage**（测试与开发路径）。
由 `StorageKind`（`memory` / `local` / `remote`）显式建模并原样上报给 UI：

```ts
export type StorageKind = 'memory' | 'local' | 'remote'
export const STORAGE_NOTICE: Record<StorageKind, string> = { ... }
```

三个页面的结果提示条都引用 `STORAGE_NOTICE`，不各写各的。

> ⚠️ **绝不要笼统地说「保存成功」。** 用户心里的「保存成功」=「线上已经是这样了」，
> 而实际可能只存在他自己的浏览器里。写入位置本身就是必须告知用户的信息。

**降级是诚实的**：SSR、隐私模式、配额写满时仓储把 `storage` 降级为 `memory`，
UI 如实说「只写入了内存」。**写失败绝不假装成功。**

**数据源三态不能混为一谈**：`ready`（是否已拉取）/ `error`（失败原因）/ `dataOk`。
远程仓拉取那几百毫秒里如果直接渲染「空列表」，用户看到的是「我的数据全没了」。
三个后台页面都用 `<AdminDataState v-if="!dataOk" />` / `<div v-else>` 二选一结构，
加载中显示「加载中」、失败显示原因 + 可点的「重试 / 重新登录」。

**远程模式没有「恢复出厂数据」**：那等于用出厂内容覆盖线上数据仓。按钮不渲染，
`resetToSeed()` 也拒绝执行 —— 要回滚请对数据仓做 `git revert`。

**本地模式**的 `resetToSeed()` 把数据恢复成出厂内容（入口在「数据现状」区，页内确认），
也是存档损坏 / 原始 ID 异常时的显式修复入口。

## 4. 编辑器的信息结构

参考 YouTube Studio / B 站创作中心的**操作流**，视觉仍是 Swiss：

- **吸顶操作条**：脏状态 + 撤销 / 预览 / 保存 / 发布；下面一排分区锚点，
  有未保存改动的区块带强调色圆点。
- **右栏「发布概览」**：封面、状态、上线清单（封面 / Banner / 下载渠道）、上次保存时间。
- **`Ctrl / Cmd + S`** 保存；只在有改动且通过校验时生效，不产生空提交。
- **列表行内快捷操作**：标题直达编辑页，行内可「上线 / 下线 / 删除」；删除走二次确认弹窗，
  确认后从 `db.json` 物理移除（不是软删除）。
- 数据说明默认收起；首页 Hero 的「收录作品」统计全部条目，并注明其中多少款当前可浏览。

### 草稿态 `useAdminGameDraft`

`useAdminGameDraft` 是**工厂**（每次编辑会话一个实例），不是模块级单例：
目录状态全后台共享一份，草稿是单次会话私有的。

`gameToDraft` / `draftToPatch` / `validateDraft` 都是纯函数导出，断言可直接测，不必构造组件。
校验与转换各只有一处职责 —— 不要在组件里重写。

草稿实例可以通过 `useAdminGameDraft({ repository })` 注入隔离目录（测试 / 预览用）；
不传时使用当前后台仓储。`useAdminGames` 仍是模块级单例 —— 后台只有一份目录，
见 [`adr/0004`](adr/0004-admin-catalog-singleton-draft-takes-repository.md)。

编辑页在 `setup()` 里**同步**调用 `loadFrom()`，不能放进 `onMounted`：
否则 SSR 首帧渲染空表单、客户端再填上，既造成 hydration 不一致，也让冒烟断言不到字段值。

**草稿实例通过 `provide` / `inject` 共享**（`provideAdminGameDraft()` / `useAdminGameDraftContext()`）。
子组件不要自己再调 `useAdminGameDraft()` —— 那会造出第二个实例，表现为「编辑了但草稿没变」，
完全静默、极难排查。

> ⚠️ `loadFrom` / `resetToBaseline` / `markSaved` 用 `applyDraft()` **逐字段复制**，
> 不能用 `Object.assign`：后者连数组引用一起复制，让草稿的 tags 与基线的 tags 指向同一个数组 ——
> 改草稿等于改基线，`isDirty` 永远为 false，改动静默丢失。有专条断言守着。

### 标签

标签**没有独立存储**，只是各条作品上的字符串数组。因此：

- 「重命名 / 删除标签」的本质是**改所有引用它的作品**（`renameTag` / `deleteTag`）。
  重命名到已存在的名字时合并去重。
- 「创建时间」列**不伪造日期**：只记录本次会话中后台首次引入的标签（`tagCreatedAt`），
  其余显示「—」。
- 约束（`TAG_LIMITS`：每条作品最多 12 个、每个标签最长 24 字符）在深模块的 `readTags()` 里收口；
  组件只做交互与即时反馈。
- 标签来自 `v-model` 输入框，运行时类型不受 TS 保证 → `normalizeTag()` 入参是 `unknown`。

### 下载渠道

每一行是「服务商 / 下载地址 / 提取码」，顺序即前台 `DownloadPanel` 的渲染顺序。

- **逐行校验**：深模块单独提供 `downloadErrors`（与行一一对应），`isValid` 一起判断。
  **每行只报第一条错误** —— 一行同时飘三条红字只会让人不知道先改哪个。
- 刚点「添加渠道」得到的空白行不立刻飘红（噪音不是反馈）：只有提交过一次或该行已开始填写才显示。
- 提取码留空时写成 `undefined`，与 `password?: string` 对齐。

> ⚠️ 静态提示文案不要和错误文案用同一句话，否则用户在同一屏看到两遍同样的句子，
> 分不清哪句是提示哪句是报错。

### 发布状态

`draft` 前台不可见 · `published` 前台展示 · `offline` 前台不展示但数据保留。
**下线靠改状态实现，不靠删数据。** 归档与状态正交（见 [`ARCHITECTURE.md`](ARCHITECTURE.md) §2）。

| 入口 | 语义 |
| --- | --- |
| 列表页批量 / 行内操作 | **立即生效**（快捷动作） |
| 编辑页「保存 / 发布」 | 只改草稿，点保存才落库 |

「保存」按表单当前内容落库；「发布」=「状态切到已上线 + 保存」的快捷方式，共用同一套校验。

**发布级校验（`gamePublishIssues`）**：状态是 `published` 时必须有三项 —— 封面、Banner、
至少一个下载渠道（前台都直接渲染：没封面列表卡片一片空白、没 Banner 详情页顶部裂图、
没下载渠道这个资源导航条目没有意义）。草稿不受限制，所以它不能塞进 `isValid`，
而是单列并由 `canSave` 一起判断。

同一判据也在仓储 seam 上执行（`validateGameWrite`），所以批量上线、行内切换、GameJolt 导入
都不能绕过它；失败会进入批量结果的 `failed` 并显示原因。

> ⚠️ 状态脏值一律降级为 `draft`（`readStatus`）：宁可少发布一条，也不能因为脏值把内容误公开。

## 5. 图片

### 上传（Phase 16）

登录后**选图即上传**：文件以二进制写进数据仓，返回的**完整外链**写进作品数据。

```
images/games/<作品slug>/<位置>-<时间戳>.<扩展名>
例：images/games/tjoc-reborn/cover-20260930204133.png
```

前台零改动：返回的是完整外链，`assetUrl()` 原样放行。

| 决策 | 理由 |
| --- | --- |
| 文件名带**毫秒时间戳 + 4 位随机后缀** | 图片是公开地址、会被缓存；换名即换地址。只精确到秒时，同一秒内连传两张会撞同一路径、第二张覆盖第一张，图库凭空少一张 |
| 按**作品 slug** 分目录 | 仓库里翻找图片时看得懂；新作品无 id 时用标题 slug |
| 上传期间**禁用入口** | 否则重复拖放会传上去好几份 |
| 本地模式**明确抛错** | 而不是返回假地址 —— 后者让用户以为已经上传成功 |
| 上传前**自动压缩** | 长边超过位置上限就等比缩小，非 GIF/SVG 转 WebP（quality 0.88）；转完更大时保留原图。压缩在 composable 层，仓储只负责原样存字节 |

> ⚠️ `putFile` 与 `putBinaryFile` 是两个函数：文本走 UTF-8 → base64，图片字节必须原样 base64。
> 两者的 base64 助手共用（测试桩也要用同一份，各写一份会一起错、互相掩盖）。
>
> ⚠️ 测试桩**不能把所有 PUT 都当成改 `db.json`**：图片上传写的是另一个文件。
> `src/dev/adminAssertions.ts` 的假 GitHub 与 UI 测试的 `page.route` 都按路径区分。

### 尺寸检查（`utils/imageInspect.ts`）

刻意分两层：`readImageSize()`（浏览器侧读位图尺寸，需要 DOM API）与
`checkImageSize()`（纯函数，只看尺寸判断能否收）。纯函数才测得到，不必伪造位图。

| 规则 | 处理 |
| --- | --- |
| 宽度 < 640（图库 400） | **拒绝** —— 放到卡片上会糊 |
| 单边 > 8192 像素 | **拒绝** —— 仓库和带宽吃不消 |
| 比例偏离建议值 > 25% | **只提示** —— 前台用 `object-contain`，比例不对只留白。硬拦截会让人为一张略扁的封面反复裁图 |

校验顺序是**类型 → 大小 → 尺寸**：尺寸检查要先把图读成位图，最贵，所以放最后。

**上传进度**是「正在上传第 N / M 张」，**不是百分比**：`fetch` 不暴露上传进度，
字节级要换 XHR，会引入第二条 HTTP 路径、测试桩也要写两份，不值得（4 MB 上限）。

**失败重试**：上传失败把文件记下来，就地给「重试」按钮（图库是「重试这 N 张」）。

### 删除旧图：时序最要紧

> 清理**必须放在保存成功之后**。上传那一刻新图还没被任何作品引用，而旧图仍是线上正在用的那张 ——
> 那时删旧图等于把线上正在显示的图删掉。

三道闸：① 只清理数据仓 `images/games/` 下的图（站内旧资源与外部图床一律不碰）；
② 只清理没有出现在任何作品里的（包括刚保存的那条）；③ 清理失败绝不让保存失败。

### 本地临时预览

没有存储层，本机文件只能用 `URL.createObjectURL()` 生成 `blob:` 地址 —— 只在本页有效、刷新即失效。
这类值必须显著标注「本地临时预览 · 未上传」，不要去掉标注；
blob 地址在替换时与组件卸载时撤销（`URL.revokeObjectURL`）。

> ⚠️ **归一化函数不要做「上限截断」**。`readTags()` / `readGallery()` 同时被 `draftToPatch()` 使用；
> 在其中按上限截断，会让超限作品在保存时**静默丢掉多余数据**。上限在新增入口
> （`addTag()` / `addImages()`）与仓储写入边界各执行一次，越界是显式报错而不是截断。

封面 / Banner 允许留空（草稿阶段可以先没图）；填了就必须是站内路径或 http(s) 地址。

## 6. 预览（Phase 18）

编辑页操作栏的「预览」**开一个新标签页**，渲染 `views/GameDetail.vue` **本身** ——
不是另写一个「像前台」的预览页（副本迟早分叉，分叉后预览就在骗人）。

| 决策 | 理由 |
| --- | --- |
| **新标签页** | 导航去预览页会卸载编辑页，而草稿是每个编辑会话一份的 —— 卸载即丢弃 |
| 草稿经 **localStorage** 交接，读完即清 | 跨标签页只能靠 storage。⚠️ `sessionStorage` **不跟着 `window.open` 的新标签页走** |
| 预览路由挂在 **`/admin` 下** | 显示的是未发布内容，不能有公开地址；父路由自动带登录门禁 |

不需要已保存：改到一半也能预览。预览数据以已保存的那条为底（保住 metrics 等不可编辑字段），
再把草稿盖上去。预览页有醒目说明「不会对外可见，也不会写进数据仓」；刷新预览页显示空状态。

预览使用 `useViewCounter({ track: () => false })` 跳过计数 —— 否则管理员每预览一次都在刷量。

## 7. 操作署名（Phase 19）

数据模型有 `updatedBy?: string`（最近一次修改者，GitHub 账号名），与 `updatedAt` 一样
**由仓储管理、调用方不写**；远程仓储每次写入打上当前操作者。

**为什么不做独立的 `audit_logs`**：git 历史本身就是完整审计日志 —— 每次保存都是一次提交，
作者是操作者、提交信息写清改了什么、时间戳天然存在，免费、可 diff、可 revert。
再维护一份是冗余，还要付出并发追加撞车、多一次 API、多一个失败点的代价。

`account` 传给仓储的是**取值函数**而不是字符串：页面刷新后令牌从本机恢复、
账号要等一次 `/user` 才拿得到 —— 传函数保证写入时取到的是**当下**的账号。

本地模式没有账号，`updatedBy` 保持缺省，界面显示「—」，**不伪造署名**。
