# 开发任务：FNAF Fan Games Archive 结构化游戏资料库与索引系统升级

## 一、项目背景

项目仓库：

https://github.com/DaXiGua732/fnaf-fan-games-archive

线上地址：

https://daxigua732.github.io/fnaf-fan-games-archive/

参考网站：

- VocaDB：https://vocadb.net/
- VocaDB 源码：https://github.com/VocaDB/vocadb
- FNaF Max Mode List：https://fnafmml.com/
- All Modes List：https://allmodeslist.pages.dev/

本项目是一个专门收录 Five Nights at Freddy's（FNAF）同人游戏的资料与资源导航网站。

目前项目已经具备游戏列表、详情页、搜索、基础筛选、游戏标签、作者管理、后台编辑、图片上传、发布状态控制等功能。

本次任务不是重写现有网站，也不是照搬其他数据库网站，而是在现有系统上逐步建立更完整的游戏资料标准、玩法分类体系和可相互导航的索引系统。

## 二、核心目标

将网站从以游戏展示和下载资源导航为主的站点，逐步发展为一个结构化、可检索、可关联的 FNAF 同人游戏资料库。

主要目标如下：

1. 建立统一、可维护的游戏玩法分类体系，重点支持「传统守夜式」「漫步探索式」等玩法类别。
2. 规范每款游戏的属性数据，明确标准字段、玩法类型、游戏机制和自由标签之间的区别。
3. 让游戏详情页的作者、玩法、标签、平台、引擎、系列等属性成为可点击的索引入口。
4. 支持多个条件组合筛选游戏，而不局限于当前已有的作者、年份、系列筛选。
5. 建立游戏之间的明确关联，包括前传、续作、重制版、重启作品、衍生作品等。
6. 在后台提供相应的数据录入、编辑、维护和校验能力。
7. 尽量复用现有架构与代码，保持 GitHub Pages 静态部署和当前数据仓方案，不要为不必要的功能引入复杂后端。

最终目标是让用户可以从任意一款游戏出发，通过玩法、开发者、标签和作品关系不断发现其他游戏。

## 四、功能一：建立规范化的游戏资料模型

### 4.1 重新梳理游戏属性

在现有模型基础上采用增量方式扩展字段，不要破坏已有记录。

需要区分以下信息：

**标准资料字段**

包括游戏名称、作者或开发团队、发行年份、所属 IP 系列、开发引擎、支持平台等。

在不显著增加维护负担的前提下，可以考虑支持其他名称、官方页面或原始发布页面等字段。是否新增应以审计结果为准。

**玩法类型**

描述游戏主要采用什么类型的玩法，例如：

- 传统守夜式
- 漫步探索式
- 其他经过资料整理后确定的玩法类型

允许一款游戏具有多个玩法类型，或指定一个主要玩法类型和若干次要类型，以便表达混合玩法。

上述分类只是初始示例，不要在没有资料依据的情况下将示例视为完整的行业标准。

**游戏机制**

描述游戏具体包含哪些玩法机制，例如监控摄像头、资源管理、潜行、解谜、自由移动等。

这些机制需要与整体玩法类型区分。例如，使用监控摄像头可能是一项机制，但不一定足以决定整个游戏的玩法类别。

**自由标签**

继续保留现有 `tags` 字段，用于描述风格、题材及其他无法由专用字段表达的特征。

不要把平台、开发引擎、作者等已有的标准资料全部重复塞进自由标签。

**开发状态与网站发布状态**

严格区分游戏自身的开发状态与网站上的发布状态。

例如，一款已取消开发的游戏仍然可以在网站上公开收录。不要让游戏开发状态影响网站的发布、下线或归档逻辑。

### 4.2 分类词汇表

分类体系必须可维护，而不是散落在组件代码里的硬编码字符串。

根据现有后台架构，设计合理的分类词汇表或分类管理机制。每个分类项应尽量具备稳定的标识、显示名称和简短定义。

分类维护应考虑：

- 创建和编辑分类。
- 重命名分类时同步处理已有作品。
- 显示分类被多少作品使用。
- 防止重复分类及含义高度重叠的分类。
- 删除仍被作品引用的分类时提供安全处理。
- 为混合玩法提供合理的多选方案。
- 为暂时无法确定类别的作品保留未分类或待核实的处理方式。

应优先采用满足需求的最小数据模型，不要为了形式而建立复杂的多层分类系统。

如果需要新增管理页面，应复用现有后台布局和交互模式。

## 五、功能二：可点击的游戏属性索引

将游戏详情页中的关键属性从静态文字转换为能够导航的索引入口。

至少考虑以下维度：

- 开发者或作者。
- 主要玩法和次要玩法。
- 游戏机制。
- 自由标签。
- 支持平台。
- 开发引擎。
- IP 系列。
- 发行年份。

用户点击相应属性后，应该能看到与该属性匹配的游戏集合，而不是进入空白页面或只显示一段文字。

例如：

- 点击「漫步探索式」后，查看具有该玩法分类的全部可见作品。
- 点击某个开发者后，查看该开发者的其他作品。
- 点击某个机制标签后，查看包含该机制的其他游戏。
- 点击开发引擎后，查看使用同一引擎的游戏。
- 点击年份或 IP 系列后，查看相应的作品集合。

实现前先检查当前路由架构，决定是通过首页过滤状态、独立索引页，还是两者结合来实现。

要求：

1. 尽可能复用已有的列表、过滤和分页组件。
2. 同一个属性的索引结果必须采用统一查询逻辑。
3. 不要为每个标签手动编写独立页面。
4. 索引页面必须兼容空结果和无效属性。
5. 关键筛选条件最好能体现在 URL 中，从而支持刷新、复制链接和浏览器前进后退。
6. 索引页面只能展示符合现有公开可见性规则的作品。
7. 为移动端保留合理的操作方式。

## 六、功能三：扩展组合筛选

对现有搜索与筛选系统进行增量扩展。

至少支持以下筛选维度：

- 作者。
- 年份。
- IP 系列。
- 玩法类型。
- 游戏机制。
- 标签。
- 支持平台。
- 开发引擎。

如果现有数据和界面结构允许，可以再加入游戏开发状态等有实际用途的筛选项。

### 6.1 筛选规则

默认采用以下语义：

- 不同筛选维度之间使用 AND 关系。
- 同一维度选择多个值时，默认使用 OR 关系。
- 搜索关键词可以与所有其他筛选条件组合。
- 清除筛选后恢复完整的公开游戏集合。
- 筛选、搜索和排序变化时正确重置或调整分页。
- 筛选条件改变后，分页不能停留在不合法的页码。

例如：

玩法类型 = 漫步探索式  
机制 = 解谜 OR 潜行  
平台 = Windows

表示寻找具有漫步探索玩法、至少具有解谜或潜行机制，并且支持 Windows 的公开游戏。

如果现有交互设计确实需要不同的多选语义，先在实现计划中解释原因，再采用一致、容易理解的规则。

### 6.2 搜索行为

扩展搜索字段，使其能够覆盖有实际价值的资料，例如：

- 游戏名称和其他名称。
- 作者。
- IP 系列。
- 引擎。
- 玩法类型。
- 游戏机制。
- 标签。
- 平台。

如果加入其他名称字段，应让搜索能够识别该字段。

搜索逻辑必须集中在现有的深模块或适当的数据查询模块内，不能在多个 Vue 页面中重复实现。

### 6.3 过滤元数据

过滤面板中的选项必须与实际可见的作品一致。

不能因为某个草稿作品使用了一个分类，就让普通访客看到该分类，却发现没有可浏览的结果。

若加入结果数量展示，必须正确处理当前筛选条件与结果数量之间的关系，避免误导用户。

## 七、功能四：游戏之间的关联关系

为游戏资料库增加明确、可维护的作品关联。

至少考虑以下关系：

- 前传。
- 续作。
- 重制版。
- 重启作品。
- 衍生作品。
- 其他相关作品。

同时提供以下相关作品发现方式：

- 同一开发者或开发团队的其他作品。
- 同一 IP 系列的作品。
- 有明确资料依据的同一世界观作品。

### 7.1 关系数据规则

先审计现有模型，再设计最适合当前架构的关系数据结构。

每条显式关系应能识别关联目标游戏，并明确关系类型。需要支持以下规则：

- 不能关联到自身。
- 不能引用不存在的游戏 ID。
- 防止无意义的重复关系。
- 明确关系的方向性和显示文案。
- 适当处理关系两端的展示，不要为了在另一端显示而产生重复记录。
- 删除或变更被关联作品时，不能留下静默失效的引用。
- 后台编辑器应能选择已有作品，而不是要求管理员手工输入未知 ID。

关系类型的方向语义必须清晰。例如，应能明确区分“当前作品是另一作品的前传”和“当前作品是另一作品的续作”。

同一开发者和同一系列的相关作品，应尽量由已有标准字段派生，而不是要求管理员重复维护相同信息。

只有有资料依据的作品关系才能作为明确关系保存。不要仅因为两款游戏的标签相似，就擅自认定它们是续作或同一世界观作品。

### 7.2 前台展示

在游戏详情页增加适当的相关作品区域，显示关系类型、作品名称及必要的封面信息。

点击关联作品可以打开对应的详情页。

如果被关联作品已下线、归档或无法公开访问，不得通过关联模块绕过现有的公开可见性规则。

当某款作品没有关联数据时，应正常显示页面，不应出现空白框架或明显的错误状态。

## 八、功能五：后台管理能力

将新增数据真正接入现有后台，不能仅在前台写死测试数据。

后台至少需要支持：

1. 编辑游戏的玩法类型。
2. 编辑游戏机制。
3. 管理相关自由标签。
4. 编辑标准资料字段。
5. 维护作品关联。
6. 查找和选择关联作品。
7. 校验重复分类、无效引用和不合法的自关联。
8. 在保存之前识别可以明确发现的数据问题。
9. 在编辑器预览和保存后正确展示新增字段。

新增字段应当遵循现有后台的数据读写、图片上传、预览、保存和发布流程。

优先沿用现有编辑器的信息组织方式。不要因为新增了若干属性，就重新实现整套后台管理系统。

如果需要给管理员提供分类完整度提示，可以加入适当的提示信息，例如缺少主要玩法分类、关联作品不存在或标签不规范。但不能因为普通资料暂时缺失，就让原本合法的作品无法保存。

## 九、数据兼容与架构约束

这是本次改动的重点之一。

1. 以当前正式数据结构为准，不要假设历史字段仍然是最新实现。
2. 新增数据字段时，尽量采用向后兼容的增量设计。
3. 旧记录缺少新增字段时，应通过现有归一化机制提供合理默认值。
4. 不能因为旧数据没有玩法类型或关联记录，就导致整个前台无法加载。
5. 不要无条件重写所有现有游戏数据。
6. 不要把分类词汇表维护逻辑散落在多个 Vue 组件中。
7. 如果已有 Repository 或数据仓抽象，应沿用它们。
8. 不要为实现本次功能擅自引入必须长期运行的新服务器、数据库服务或复杂部署依赖。
9. 不能破坏现有后台对数据仓的读写能力。
10. 不能让前台意外暴露草稿、下线或已归档作品。
11. 如果需要进行数据迁移，应提供可重复执行、具有校验和错误报告的方案。
12. 对无法核实的分类或关联，保留待补全状态，不要自动编造数据。

在实现之前，先提出字段设计和兼容策略。不要在未经验证的情况下对现有数据仓执行大规模批量修改。

## 十、视觉与交互约束

本项目具有自己既定的视觉设计体系。

实施前先审计当前代码和样式规范，遵循当前实际生效的设计规则与主题系统，包括已有的颜色主题或深浅色模式（如果已实现）。

具体要求：

- 不要进行无关的整体 UI 重设计。
- 不要随意引入圆角、阴影、渐变或大幅位移动效。
- 不要在组件中硬编码与现有主题体系冲突的颜色。
- 不要破坏当前的字体、网格、间距、边框和交互风格。
- 属性索引应易于识别，但不能把页面变成大量无差别的彩色标签。
- 筛选面板需要在桌面端和移动端都能正常使用。
- 键盘操作、焦点状态和必要的无障碍语义不能被忽略。
- 新增空状态、加载状态和错误提示时，保持现有设计系统一致。

## 十一、必须遵守的代码质量规则

遵守现有项目文档中的工程约束。

尤其注意：

1. 不要绕开现有的深模块设计。
2. 不要在 Vue 视图组件中手写 `.filter()` 或 `.sort()` 数据加工逻辑，除非审计确认项目规范已经改变，并获得明确批准。
3. 搜索、筛选、排序、分页等查询逻辑必须集中在现有数据查询模块或适当的共享模块中。
4. 不要在不同组件之间复制粘贴相同业务规则。
5. 不要为了让测试通过而删除、弱化或绕过现有断言。
6. 不要将具体游戏名称和当前条目数量写死在测试预期中。
7. 不要提交包含真实访问令牌、密码或敏感认证信息的文件。
8. 不要让公开页面依赖必须成功的网络请求才能首次渲染。
9. 遵循当前 TypeScript 类型规则，避免使用宽泛的 `any` 规避类型检查。
10. 不要未经必要性论证就增加大型依赖。

## 十二、分阶段实施计划

完成审计和设计后，按以下方向逐步推进。具体阶段边界应结合现有代码结构调整，但不能跳过审计或一次性进行大规模无关重构。

### Phase 0：审计和设计冻结

完成代码审计、需求拆分、字段设计、查询逻辑设计、作品关联设计、风险分析和验收标准。

本阶段原则上不进行业务代码修改。

输出明确的阶段计划和需要重点关注的兼容风险，等待确认。

### Phase 1：数据模型与分类基础

新增必要的数据类型、分类词汇表和归一化规则。

确认旧记录能够正常读取，新增字段有明确语义，开发状态和网站发布状态互不混淆。

完成类型检查与适当的单元测试。

### Phase 2：后台分类与资料编辑

在现有后台编辑器中加入玩法类型、游戏机制及必要的分类维护能力。

确认分类的创建、编辑、重命名、删除限制、保存和重新读取逻辑正常。

### Phase 3：前台可点击属性索引

将详情页中的关键属性转换为索引导航。

实现对应的列表结果、必要的路由状态和空结果处理。

不重复实现查询逻辑。

### Phase 4：组合筛选和搜索增强

扩展现有数据查询模块及过滤面板。

实现不同筛选维度的交叉查询、明确的多选语义、搜索增强和分页状态处理。

### Phase 5：作品关联关系

实现关联数据结构、后台关系编辑、目标校验和前台相关作品展示。

保证关系方向性明确，关联数据失效时能够被发现和修复。

### Phase 6：集成验证与资料质量检查

完成跨模块检查、旧数据兼容测试、公开页面可见性测试、组合筛选测试和关联关系测试。

## 十三、验收标准

最终实现至少应满足以下条件。

### 数据与后台

- 旧游戏数据可以正常读取、编辑、保存及重新加载。
- 新增字段在前后台具有一致的含义。
- 后台能够维护玩法类型与游戏机制。
- 标签和分类不会因为轻微的命名差异被无限重复创建。
- 关联目标选择和校验正常工作。
- 非完整资料不会无故阻止合法作品保存。
- 不会自动捏造游戏分类或作品关系。

### 前台索引

- 详情页关键属性可以点击并打开正确的索引结果。
- 每个索引结果与对应筛选条件一致。
- 无结果和无效索引具有合理的页面状态。
- 索引结果只包含符合现有公开可见性规则的作品。
- 刷新页面和复制链接不会无故丢失已编码在 URL 中的筛选状态。

### 组合筛选

- 玩法类型可以与机制、平台、开发者等条件组合。
- 同维度多选按照确定的规则工作。
- 搜索词和筛选条件可以同时生效。
- 清除筛选、排序和分页行为正常。
- 不出现筛选选项存在但结果永远为空的隐性错误。

### 作品关系

- 可以维护前传、续作、重制版、重启作品和衍生作品等关系。
- 自关联、无效目标和不合理的重复关系能够被拒绝或明确提示。
- 从详情页能够打开相关作品。
- 目标作品下线、归档或删除时，关联展示不会绕过权限或可见性规则。

### 工程质量

- TypeScript 类型检查通过。
- 现有测试没有被无理由削弱。
- 现有的 `npm run verify` 全部通过。
- 按项目规范需要执行的构建、冒烟测试、数据导入和后台专项测试均已执行。
- 如果某些 UI 或 E2E 测试只能在特定本地环境运行，应明确说明，而不是声称已经全部验证。
- 没有无关的大规模重构或不可逆的数据操作。

每个阶段按照以下顺序执行：

1. 说明本阶段的目标、涉及的模块和预期变更。

6. 检查 Git diff，确认没有不相关改动、敏感信息或意外的大规模数据变化。
7. 更新相关文档。
8. 汇报实现内容、修改文件、测试结果、已知问题和下一阶段计划。
